02 / What each stage actually does

  1. BIP-39 — mnemonic → seed. The 12-word phrase is an encoding of entropy plus checksum. PBKDF2-HMAC-SHA512 derives a 64-byte seed (2048 iterations; salt “mnemonic” + optional passphrase).
  2. BIP-32 — seed → HD tree. HMAC-SHA512 with key “Bitcoin seed” creates a master private key and chain code. Child keys are derived by hardened or non-hardened steps.
  3. BIP-44 — path convention. The Ethereum path m/44'/60'/0'/0/i defines purpose, coin type, account, change and address index. It is not a cryptographic primitive.
  4. secp256k1 — private → public. Scalar multiplication Q = dG generates a public key on a large elliptic-curve group; it does not encrypt the mnemonic or hash it.
  5. Keccak-256 — public → 20-byte address. Hash the 64-byte uncompressed public-key coordinates (without the 0x04 prefix), then take the last 20 bytes.
  6. EIP-55 — checksum encoding. Hash the lowercase hexadecimal address as ASCII using Keccak-256, then apply letter case according to hash nibbles. It detects many typing mistakes; it provides no authentication.

03 / Derivation versus generation

Generating high-entropy randomness, deriving child keys from a seed, multiplying an elliptic-curve point, hashing a public key and encoding a checksum are distinct operations.

Key generation

A secure wallet begins with high-quality randomness. A mnemonic's human-readable words do not create randomness themselves.

Key derivation

PBKDF2 and HMAC deterministically expand/derive key material and enable hierarchical accounts. The BIP-44 path merely chooses a location in the tree.

Public-key operation

Scalar multiplication establishes the one-way private/public relation used by digital signatures.

Hashing and checksum

Keccak compresses the public key into an address; EIP-55 detects many transcription errors via mixed case.

04 / Statistical properties

Idealized behavior is meaningful only under explicit assumptions about input entropy and cryptographic hardness.

StageExpected property / caveat
BIP-39 entropyUnpredictable source; a 12-word mnemonic typically encodes 128 bits of entropy plus 4 checksum bits.
PBKDF2 / HMACDeterministic outputs, pseudorandom appearance given suitable cryptographic assumptions; no new entropy is created.
secp256k1Uniform private scalars map bijectively to non-identity group elements (for generator of prime order).
Keccak-256Avalanche-like changes and uniform-looking digests expected; a hash is not encryption.
160-bit addressUnder an ideal uniform model, collision probability for q distinct samples is approximately q(q−1)/2¹⁶¹ when q is small.
EIP-55Formatting provides a checksum; case changes do not add address entropy or secrecy.

Statistical checks can reveal obvious bias but cannot prove cryptographic security. Poor or reused initial entropy makes every deterministic downstream stage predictable.

05 / Keccak versus SHA3-256

Ethereum uses legacy Keccak-256, which is based on the Keccak sponge construction. NIST standardized SHA3-256 with a different domain-separation/padding convention. Both produce 256-bit digests, but their outputs differ for the same message.

Keccak-256("") =
c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470

Do not use Web Crypto SHA-256 or SHA3-256 as a drop-in replacement for Ethereum's Keccak-256.

Why not one algorithm?

No single primitive solves all problems: entropy and key management, deterministic key hierarchy, asymmetric signatures, shortening a public key, and detecting user typing errors have different mathematical purposes and different security requirements.

Conclusion

Ethereum wallet addresses are derived through a chain of cryptographic constructions with separate responsibilities. The pipeline is deterministic, while its security relies on secret input entropy, secure elliptic-curve arithmetic, collision-resistant hashing and careful handling of key material. Statistical output appearance alone does not establish safety.
